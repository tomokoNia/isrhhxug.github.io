# 用 Wireshark 从 QQ 服务器到 PC 的流量中还原手机发送的 JPG

> 一次"抓包还原图片"的完整复盘：怎么筛会话、怎么找包、怎么截 JPG，以及一个绕不开的思考——既然 QQ 缓存里就有，为什么还要在 Wireshark 上费劲？

## 背景与结论先说

我在校园网环境下，用 Wireshark 抓 PC 与 QQ 服务器之间的流量，成功把手机端发往"我的电脑"的一张 JPG **完整还原**出来。由此**实测证实**：本次场景下，**QQ 服务器到 PC 端的这一段数据是未加密的**（至少图片 payload 以明文 JPEG 字节流传输）。

整个过程里，**最难的环节不是截文件，而是"找到那个需要的数据包"**。下面按我实际走过的路径复盘。

## 一、环境与目标

- 手机 QQ → "我的电脑"发送一张 JPG
- PC 连校园网，手机走移动网络，**不在同一局域网**
- 因此 PC 抓不到"手机 IP"，只能抓到 **PC ↔ 腾讯服务器** 这一段
- 目标：从这段流量中把 JPG 还原出来，并判断是否加密

## 二、最关键也最难的一步：找到"那个包"

### 我的方法：从「会话统计」反推服务器 IP

没有去死磕 `netstat` 查 PID，而是直接用了 Wireshark 的 **Statistics → Conversations**：

1. 开始抓包
2. 在 PC QQ 上触发接收（手机发图）
3. **停止抓包**，打开 **Statistics → Conversations → TCP**
4. 按 **Bytes** 排序，找"操作 QQ 那一刻流量突增"的会话
5. 右键该会话 → **Apply as Filter → Selected → A ↔ B**

过滤器自动生成类似：

```text
ip.addr == 113.96.x.x and ip.addr == 192.168.x.x
```

这条流对端就是 **QQ 服务器 IP**，会话被精确圈定。

### 为什么说"找包"最难

- QQ 同时连多个服务器（登录、消息、文件、CDN），会话一大堆
- 校园网还混着认证门户、代理的流量，干扰多
- 加密与否、哪条流承载图片，**只有点开 Follow Stream 才知道**
- 一旦筛错会话，后面截取全是白费

**经验：先用 Conversations 按流量突增锁定会话，再 Follow Stream 验证内容，比一上来查 PID/IP 高效得多。**

## 三、确认是否加密

锁定会话后，三步判定：

| 检查 | 结果 | 结论 |
| --- | --- | --- |
| Follow TCP Stream | 能看到 `FF D8` 开头的二进制，非全乱码 | 疑似明文 |
| 搜测试字符串/图片特征 | 能定位到 JPEG 结构 | 明文 |
| 熵值 / TLS 握手 | 该流无 TLS 握手，payload 有结构 | **未加密** |

> 说明：本次实测该图片流为明文 JPEG。但 QQ 其他流量（信令、消息）仍可能是 TLS/自研加密，**不能以偏概全**——结论仅针对本次抓到的图片传输段。

## 四、还原 JPG 的具体操作

### 1. 定位文件边界

- **文件头 SOI**：`FF D8`
- 常见完整开头：`FF D8 FF E0 00 10 4A 46 49 46`（JFIF）或 `FF D8 FF E1 ... Exif\0\0`（Exif）
- **文件尾 EOI**：`FF D9`

### 2. 截取

- Follow TCP Stream → Show data as **Raw**
- 从 `FF D8` 开始，取到该流中对应的 `FF D9` 结束
- **Save as** 存成 `.jpg`

### 3. 校验

```bash
file 还原.jpg          # 应显示 JPEG image data
exiftool 还原.jpg      # 可读出设备、时间、甚至 GPS
```

能正常打开 + `file` 识别为 JPEG，即还原成功。EXIF 里往往还能读到拍摄设备、时间、GPS——**元数据有时比图本身信息量更大**。

### 4. 备选工具

```bash
tcpflow -r 抓包.pcapng -o out        # 按流自动落盘
tshark -r 抓包.pcapng --export-objects http,out   # 若走 HTTP
```

## 五、我的思考：缓存里就有，为什么还要在 Wireshark 上费劲？

这是整个过程中我反复问自己的一句话，也是这篇博客最想留下的部分。

**客观上，QQ 的本地缓存路径里确实能找到接收到的图片文件**——聊天记录里的图、文件传输的落盘，都在本地有副本。既然如此，抓包还原看起来像是"多此一举"。但我最后认为，这两件事解决的是**完全不同的问题**：

### 1. 缓存是"结果"，抓包是"过程"

- 缓存告诉你：**收到了什么**
- 抓包告诉你：**数据是怎么来的、走哪条路、在哪个环节是什么形态、有没有加密**

缓存里是一张已经落盘的图；抓包里是"服务器→PC"这段链路上**原始字节的样子**。我想验证的是**传输是否加密**，这个问题的答案**只存在于链路中，不存在于缓存里**。

### 2. 缓存不可控，链路可观测

- 缓存路径、命名、是否分片、是否被清理，都由客户端决定，**不可控、不可复现**
- 抓包是**旁路观测**，不改客户端、不依赖版本，能看到协议层真相

### 3. 这是一次"学习/验证"而非"取文件"

如果目的只是拿到图，缓存当然最省事。但这次的目的有三个，**缓存一个都满足不了**：

1. **验证加密与否**（安全认知）
2. **理解 QQ 传输的协议与路径**（P2P 还是中转、明文还是 TLS）
3. **掌握抓包定位与文件重组的通用方法**（可迁移到其他协议/场景）

### 4. 合规视角：缓存是"你的"，链路分析要"授权"

- 读自己设备的缓存，天经地义
- 抓包分析链路，**必须在自有设备、自有账号、明确授权**下做

### 一句话总结这个思考

> **缓存回答"我收到了什么"，抓包回答"它是怎么来的、安不安全"。** 前者是结果，后者是真相。费劲抓包，不是为了那张图，而是为了搞清楚"这张图在链路上到底长什么样"——这恰恰是缓存永远给不了的。

## 六、经验清单（可复用）

1. **筛会话**：Statistics → Conversations → TCP → 按 Bytes 排序 → 流量突增那条 → Apply as Filter
2. **找包**：先触发操作再停抓，时间对齐 + 搜特征字节
3. **判加密**：Follow Stream 看乱码 / 搜测试串 / 看 TLS 握手 / 算熵
4. **截文件**：JPG `FF D8`→`FF D9`；GIF `GIF89a`→`3B`；PNG `89 50 4E 47`→`IEND`
5. **校验**：`file` + `exiftool`
6. **合规**：仅自有设备/账号/授权环境

## 七、免责与边界

- 本文所有操作均在**本人设备、本人账号**下完成
- 抓取/还原**他人**通信涉嫌违反《网络安全法》《个人信息保护法》
- 本次"未加密"结论**仅针对实测的图片传输段**，不代表 QQ 全部流量；QQ 信令/消息等仍可能加密

## 结语

这次最大的收获不是"还原出一张 JPG"，而是两件事：

1. **找到了"最难的一步"的方法论**——用会话统计反推服务器 IP，比盲查 PID 高效；
2. **想清楚了一个看似多余的问题**——缓存与抓包各司其职，**前者给结果，后者给真相**。

费劲抓包，值不值？如果你的目标是"理解链路"，那就值。
